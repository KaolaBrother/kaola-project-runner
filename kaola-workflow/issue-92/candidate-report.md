## The measured defect

`scripts/kaola-acp-holder.py` sent exactly one `permission_required` carrier event per new pending
request (Issue #76). A pending permission keeps the worker turn **active**, so no turn-end `idle`
ever follows it. If the bound ZCode Host holder was not listening at that moment the send recorded
`host-unreachable` in the worker's own log and nothing else happened — the wake was gone for good.

Raw baseline receipt, `evidence/01-baseline-loss-probe.log`, 90 s after the **same** authorized
Host restarted:

```json
{"host_staged_worker_events": [], "host_delivered": [], "host_prompts": [],
 "worker_carrier_sends_total": 1, "worker_turn_active": true,
 "worker_pending_permissions": [{"request_id": "zc-1", ...}]}
```

## The recovery trigger (the thing to review)

The worker holder **retains** the undelivered `permission_required` and re-offers it from the
**holder's existing 15 s `idle_watcher` watchdog tick**. `_flush_undelivered_wakes` has exactly one
caller — `scripts/kaola-acp-holder.py:3457`, inside `idle_watcher`. No new thread, loop, scheduler,
registry, ledger, or transport gate was added.

- **No finite window.** Nothing counts attempts down or expires. The wake lives exactly as long as
  the request it locates. Pinned structurally by `test_the_retention_has_no_retry_deadline`,
  because elapsed time cannot prove a cap absent: the only three drop reasons the code can produce
  are `permission-settled`, `agent-exited`, `host-answered`, and no attempt count is compared
  against a threshold.
- **No duplicate prompt or approval.** The retry re-sends the **original `params` object**, so
  `event_cursor` and therefore the Host's deterministic `event_id` are unchanged and the existing
  Issue #90 dedup answers the repeat.
- **Owed is decided by whether the Host ever TOOK the event**, not by an error-code allowlist.
  `CARRIER_UNDELIVERED_CODES = ("host-unreachable", "host-closed", "host-reply-invalid",
  "unknown-op")` — it was not listening, hung up, answered something that is not a worker-event
  receipt, or is an older build with no such op. Each can still come good when the Host comes back.
  Anything else is the Host's own answer and settles the debt, refusal included; of the refusals
  only `worker-event-queue-full` records anything Host-side, and what it records is the overflow
  full-check that drives a full pending-approval pass anyway.
- **Delivery is proved positively, by the EXACT event.** `op_worker_event` names the event it took
  on every accepting path, so a reply carrying neither a usable string error `code` nor the exact
  `event_id` that was sent leaves the wake owed instead of silently retiring it.
- **A wake that dies BEFORE the write is not sent.** `still_owed` is re-read immediately before the
  socket write, so a settled request, an exited agent, or a begun stop aborts that offer. This
  narrows the window; it does not close it, and nothing here claims otherwise — a settlement after
  the write leaves the Host holding a locator for something already gone, recorded as
  `heartbeat_carrier_delivered_stale`, and handled by the Host's own freshness re-read.
- **Stale is dropped worker-side.** A settled request or an exited agent never becomes a Host
  prompt; a Host that still acts on the locator gets the ordinary `no-pending-permission` refusal.
- **Locator only, approves nothing.** `platform`, `session`, `repo`, `reason`, `event_cursor`,
  `request_id`. No title, options, tool input, command, or credential. The Host decides
  `permit`/reject inside its own authorization; the ordinary turn-end `idle` follows a permit.
- **Observable instead of silent.** `observe`/`status` report `undelivered_worker_events`
  (locator + attempts + last error). Event kinds: `heartbeat_carrier_undelivered`,
  `heartbeat_carrier_recovered`, `heartbeat_carrier_dropped`.
- **Out of scope is unchanged.** Ordinary `idle`/`terminated` stay one-shot, unbound workers
  (`heartbeat_host is None`) early-return, non-ZCode Hosts are untouched, the 600 s idle-exit is
  intact.

## Outer RE-review REJECTED `f5bb239` — the claim was false, and is withdrawn

**The reviewer is right, and I reproduced their race on my own tree before changing anything**
(`evidence/07-post-write-race-probe.{py,log}`). The peer takes the offer, withholds its receipt
while a real settlement empties `pending_permissions`, then answers with the exact `event_id`.
Result on `f5bb239`: `peer_offers: 1`, `pending_permissions: {}`, `undelivered_wakes: {}`, and a
`heartbeat_carrier_recovered` — a delivery with no live approval, recorded as a recovery.

**My `still_owed` check cannot be atomic and I should not have written as if it were.** Check,
write, and the Host's own staging are three steps across two processes. The pre-write re-read
narrows the window; it cannot close it. The README and CHANGELOG sentence "A wake that stops being
owed while an offer is in flight is never sent" was **false** and has been removed, not softened.
No no-stale-send semantics are claimed anywhere now.

**What replaces it — two facts kept apart.** Carrier delivery is not a live approval. A delivery
whose request died in flight is recorded as `heartbeat_carrier_delivered_stale`, carrying the reason
that overtook it and the Host's own receipt, and is never recorded as
`heartbeat_carrier_recovered`. The wake really was delivered and the record says so; what it no
longer says is that an approval is waiting.

**Safety lives on the Host side, and is now pinned by test.** The dispatch reference already said
"The event carries only `request_id`: decide it from the worker's live `pending_permissions`", and
the heartbeat prompt already said to re-read current `pending_permissions`, ignore a vanished
request idempotently, and approve nothing from the event itself. What was missing — and what my own
earlier sentence overclaimed — is that an arriving wake may already be settled; the prompt now says
so, and `test_the_host_contract_requires_fresh_verification` pins all five obligations on the
generated surfaces plus the behaviour: acting on a stale locator is refused with
`no-pending-permission`, never re-approved. At-least-once and the `event_id` dedup are untouched.

**No atomic boundary was attempted.** It is not reachable across this transport without a withdrawal
op and Host-side un-staging — new surface, and the wrong trade for a Host that must re-verify
freshness anyway. Recording the truth is the honest fix.

**Failure-first custody:** both new tests FAIL on `f5bb239` —
`evidence/06-f5bb239-rerereview-regression.log`. Note that the first three checks of the
late-settlement test PASS there too: the delivery genuinely happened on both candidates. Only the
recording was false.

**The missing claim record.** `kaola-workflow/issue-92/workflow-state.md` is now in the frozen tree,

## Outer review REJECTED `f2d141c` — both defects fixed in `0ed31b7`

**1. An accepting receipt was trusted on `isinstance(event_id, str)` — any string.** `event_id` is
deterministic, so a blank one, another worker's, or one for a different cursor or kind proved
nothing about this wake. Worse than a missed recovery: the wake was retired and a
`heartbeat_carrier_recovered` was logged for a delivery that never happened, so a loss was recorded
as a success. The worker now derives the id the Host will build (`worker_event_id()`, the same four
fields `op_worker_event` uses) and accepts only an exact match; anything else stays owed as
`host-reply-invalid` and emits no `recovered`.

**2. Staleness was checked once, before a send that can take up to `HEARTBEAT_NOTIFY_TIMEOUT`.** A
`permit` settling the request, the agent exiting, or a stop beginning inside that window still
staged the event, so the Host was prompted for a permission nobody could answer. `_carrier_send`
now takes a `still_owed` predicate re-read immediately before the bytes go out — as late as this
transport allows — and an offer that lost its reason is aborted **before the write**, recorded as
`heartbeat_carrier_dropped` with the reason that ended it. `op_stop` sets `stop_requested` before
it cancels pending permissions, so `stopping` joins `permission-settled` and `agent-exited`: the
reason vocabulary is now four.

Same event id, no new scheduler, registry, or auto-approval — the retry still re-sends the original
params, so the Host's dedup is untouched.

**Failure-first custody.** Both new tests FAIL on `f2d141c` and pass at `0ed31b7`:
`evidence/05-f2d141c-outer-defect-regression.log`. They are deterministic, not timing-dependent:
each racing cause is injected at the exact interleaving — the flush's own check still sees a live
request, and it is gone by the send's last look — and the assertion is that the peer received
**nothing**, with a control proving an undisturbed wake still is offered.

**A harness defect that would have hidden defect 2:** the test peer counted a bare connect as an
offer, so an aborted send looked identical to a delivered one. Fixed — a connection carrying no
line is not an offer.

**The absent evidence paths were a real finding.** Earlier commit messages in this branch cited
`kaola-workflow/issue-92/evidence/...` paths that existed only in the main checkout's untracked
working directory, so they resolved to nothing at the SHA they were written on. The run's raw
evidence is now committed under `kaola-workflow/issue-92/` (`*.log` is gitignored and needed
`git add -f`), so every path those messages name resolves at the frozen SHA. The mission list had
drifted the same way and is reconciled in `mission-list.md`, with the superseded verdict preserved
rather than corrected in place.

## Unverified boundaries — what this candidate does NOT establish

1. **No live UAT.** Everything is hermetic: fake ACP app-servers, no real ZCode install, no login,
   no network, no model-driven approval. A live tmux smoke per the project's integration policy has
   not been run for this change.
2. **Recovery latency is up to one watchdog tick (~15 s)** after the Host returns. Bounded and
   measured (14.1 s observed), not tuned, and not configurable.
3. **A worker holder that dies with a wake owed loses it.** The retention is in memory. This is not
   a regression — the ACP request dies with the holder that owns the agent — but it means the
   guarantee is "survives Host absence", not "survives worker-holder death".
4. **Recovery requires the same bound socket path**, i.e. the same Host session name and repo. A
   Host restarted under a different session name is a different binding. That is the existing
   Issue #70 exact-binding contract, not something this change widens.
5. **`host-reply-invalid` and `unknown-op` are retried indefinitely** while the request is
   pending. If something permanently bound at the Host socket path answered garbage forever, or a
   Host stayed on an old build, the worker would keep offering every 15 s. Judged correct — both
   genuinely mean "never taken", and both can come good on a restart — but they are the two codes a
   misbehaving or stale peer, rather than an absent one, can pin.
8. **The no-cap proof is behavioural over 250 offers plus a state-shape check**, not a proof over
   all possible cap mechanisms. A cap that consulted state outside the retained entry (a module
   global, a clock read that stores nothing) would escape both pins. Three realistic forms are
   covered by mutation; the space is not exhaustively closed.
9. **`CarrierOnlyHolder` is a stub**, not a real Holder. It reproduces only the state the retention
   path touches. If that path ever needs more holder state the stub fails loudly rather than
   quietly testing nothing, but its 250-offer result is a statement about the retention functions,
   not about a live holder under concurrency. It also calls `_flush_undelivered_wakes` directly, so
   a cap introduced in the real caller (`idle_watcher`) or in the `kind == "permission_required"`
   retention gate would be invisible to it — the live tests are what cover that path.
10. **The in-flight abort closes the window to the gap between the predicate and `sendall`**, which
    is as tight as a remote peer allows — it is not atomicity. A settlement landing after the bytes
    are written is still legitimately in flight, and the Host's existing "decide from the worker's
    live `pending_permissions`" rule is what covers that.
11. **`worker_event_id()` duplicates the Host's id formula** in the worker, and the test carries a
    third copy so a change on either side is caught rather than mirrored. A future change to the id
    shape must update all three, and a Host built on a different shape would make every send look
    invalid and retry forever.
12. **The "no time state" assertion is an exact key set**, so any future field added to a retained
    wake breaks it, not only a timestamp. That is deliberate — a denylist of time-ish names is
    exactly the weakness that let three caps through the first version of this test — but it is a
    real maintenance cost and it fails loud, not silent.
6. **Multi-worker fan-in was not measured.** Each worker retries independently; N bound workers
   with pending approvals produce N offers per tick at recovery. Bounded by concurrent pending
   permissions, never measured under load.
7. **The control-plane prompt change is one sentence** in `heartbeat-skeleton.txt` (7257/8192 B).
   `zcode-host-dispatch.md` was deliberately left alone: it sits at 8174/8192 B and its sentences
   are pinned verbatim by the #65/#70 contract tests. The recovery is transparent to the Host — it
   receives an ordinary `permission_required` — and the existing "decide it from the worker's live
   `pending_permissions`" wording already covers a request that vanished.
