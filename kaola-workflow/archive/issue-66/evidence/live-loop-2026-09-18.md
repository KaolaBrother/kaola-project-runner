## What was prompted versus self-directed (honesty note)

Both rounds were driven by explicit operating prompts from the outer Agent, not
by the Skill alone. Beat 1's confirmation (`04-confirm.txt`) listed the four
steps in order (write the heartbeat file before dispatch, bind on the start and
check the receipt, dispatch non-blocking, end the turn as the wait), and the
rework round (`07-rework.txt`) likewise told the Host to re-read the plan,
restart the same worker keeping the binding, dispatch non-blocking, end the
turn, and not stop itself. So this run proves the mechanism works end to end
under a controlling Agent that followed the reference — it does not prove a Host
would derive those steps unprompted from the Skill text alone. What the Host did
choose for itself: reading the candidate payload and plan before answering,
holding without dispatching until authorized, the dispatch prompt's content and
scope guardrails, `--resume` over a fresh session for the rework, running the
plan's test command itself instead of trusting worker prose, both acceptance
verdicts, both exact worker stops, the `.pytest_cache` cleanup, and flagging the
missing cursor field in the send receipt.

## Findings folded back into the candidate

- The send receipt on **this baseline** returned no cursor field, so the reading
  anchor came from an `observe` before the dispatch; the Host itself flagged the
  missing field in beat 1. `dispatch_event_cursor` is an Issue #65 candidate
  addition, so the reference now names it as the preferred anchor and the
  pre-dispatch `observe` as the fallback where a build does not return one.
- ZCode tool records do not name read paths, so "verify the Host actually loaded
  the Skill" is stated in terms of plan-checkable facts and produced artifacts.

## Not verified live

- A defective heartbeat `body` in a live session (the real Host wrote a correct
  `body` first time); that path is covered by the contract tests.
- Non-ZCode hosts, PTY transport, and multi-worker concurrency were out of scope.
