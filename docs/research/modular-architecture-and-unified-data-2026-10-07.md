## 2. Four layers — existing capability (source-evidenced), true fragmentation, governance gap

**L1 OS hosting**: per-session `runtime-tmux.sh`; pluggable `--launch-backend {direct,launchd,auto,systemd-user}`; `kaola-launchd-broker.py` = narrow #266 outside-caller-survival backend (one-shot job, `start_new_session` re-parent, env allowlist); Runner-level restart tooling (`kaola-acp.py:666` drain-restart presence docstring, `:3068` rebind-host). Verified-absent: cross-platform supervision policy abstraction; Linux `systemd-user` verification.

**L2 ACP adapters**: ten `platforms/*.yaml` capability manifests + ten `scripts/adapters/*.sh` + platform bridges + shared holder (`holder_features`). Fragmentation: manifest data, adapter behavior, and bridges have separate cadences with **no versioned compatibility contract linking them** — but note KPR is NOT at zero: see §3 mechanism map.

**L3 data contracts**: KPR's three typed schemas (`kaola-record-contract.py:21-22`) with tool-enforced single-writer paths; KW's five artifacts are — per the independent audit (§5.2, in-repo report) — **multi-writer in practice** (script writers across claim.js/sink-pr.js **plus Agent-authored** files; the mission ledger's primary writer is the Agent orchestrator, claim.js:3547-3549), with **named multi-artifact transactions that are resumable step-receipt workflows, not atomic DB transactions** (claim two-artifact transaction, claim.js:1466; finalize multi-file; sink `SINK_STEPS` :1560 with idempotent skip :2395 and abort hook :1548), and **a dual code-tree digest** (`computeCodeTreeHash` adaptive-schema:1124 canonical for the gate vs `computeLandableTreeDigest` validation-runner:554, deliberately different, documented :1167-1172). Distinguish three different guarantees now stated precisely: (a) *resumable multi-artifact workflow* (KW sink/finalize — recoverable, not atomic), (b) *atomic single-file write* (KPR `StateLock`+`os.replace`, `kaola-dispatch.py:3556/:1166`), (c) *all-or-nothing across Git/external effects* (none anywhere; pushes/merges are inherently external). Verified-absent: shared cross-repo contract registry/conformance.

**L4 assembly**: render pipeline + budgets + selective install + two-commit pin + install-time rendered-vs-installed diff (`kaola-project-runner-install-verify/1`, render-skills:789). Verified-absent: runtime on-demand module loading beyond narrow flags; post-install drift monitoring.

**Governance gap (evidenced)**: free-prose files remain the cross-agent evidence layer outside the typed schemas (this workspace's #269 recurrence, worktree residue, /tmp receipt reconstruction episodes). Human prose and Git engineering evidence are legitimate and stay; the gap is an ownership/query/integrity contract for the delivery-log/report class only.

**KPR's existing hash/binding mechanism map (dot correction #3)**: payload integrity = per-file sha256 + build id in each skill's `scripts/main-skill-build.json`; manifest binding = `platform.yaml` embedded in every generated skill; release/holder binding = `accepted_revision` (Git revision) and `holder_instance_id` in every ACP receipt; install verification = the install-verify receipt diff. ## 3. Unified data management (corrected current analysis)

Identity links: per-pair links exist (dispatch↔task via `link_dispatch_to_tasks` :2127 + dispositions; run↔issue↔ledger via KW finalize/sink; session↔holder↔revision via receipts). Absent: one uniform ID scheme + general query across artifact kinds. Ownership: **asymmetric** — KPR typed schemas tool-enforced single-writer; KW artifacts multi-writer by design (Agent authors several). Concurrency: per-file locks/atomic replace (KPR); resumable step-receipt workflows (KW) — no cross-store atomicity and no all-or-nothing Git effects anywhere (external actions are inherently non-transactional; recovery is receipt-based). Active-state vs Git-evidence discipline proven in the #259/#260 closeout when typed; free prose escapes both. Install vs project data boundary documented; installed-vs-repo drift observed once (claim.js `4b02b82f→bf841bec`) and **no monitor exists for it** (install-time check only). Duplicate/missing detection is artifact-specific. Version migration is per-artifact; cross-repo version coupling is undocumented (README drift symptom).

Storage options (fair; **consistency is a property of mechanisms, not topology** — a central daemon is not inherently more consistent than an embedded DB: what matters is (a) transactions/idempotency within each store and (b) how store boundaries meet Git/external actions; each option below differs on those two axes, not on a blanket "consistency" rank): ① files+unified access layer (keeps Git evidence; weakest in-store transactions) ② embedded DB (real in-store transactions; new backup/secret story; must not bypass Git evidence) ③ service/daemon (adds remote access + a service to operate — a design cost/optional need, NOT prohibited; the owner's no-resident rule governs the KPR Host loop only).

### 3.1 Fact freshness, invalidation propagation, explicit authority (root-supplied evidence)

Root independently verified a separate consumer coordination case (CAD; root-verified GraphQL originals — cited as **root-supplied evidence**, not diagnosed or controlled here): a consumer Host acted on an old done/CLOSED snapshot without re-checking the forge, while issues #967/#526/#536 had in fact **reopened** on Oct 6 03:10/03:15; the mismatch surfaced only through an input fingerprint (c479f39a / cursor 123405) and dispatch followed from there. Also root-verified: the old index's `effective_cap` has **not** been shown to constrain the current path, and the current script does not use it.

Implications for the unified-data direction: **centralized storage alone does not solve coordination** — the architecture must model (a) fact freshness (when was each authority-bearing fact last verified against its source of truth), (b) invalidation propagation (which cached views fall when the source changes — reopen/claim/state transitions), and (c) explicit authority (which record is authoritative at decision time — forge state vs local snapshot vs index). **Minimal candidate** (root's framing, an option for dot): a fresh relevant-family reopen/claim check at the **existing** no-eligible/silent decision boundary — not a new periodic audit, timer, or global forge sweep.

Case separation (explicit — root-supplied, three distinct mechanisms, no blanket capacity explanation): **(1) KPR** initial zero-dispatch = planning/role decision (issue comment 6030420812); **(2) CAD** stale-frontier = fact-freshness failure (old done snapshot, missed forge reopen); **(3) AI** (root-verified) = dispatch deferral to a later heartbeat **plus conflating an acceptance dependency (R08) with a start dependency (R10)** — after correction, 3 workers actually run (2×Sonnet R09/R10, DSH #1671); no cluster-capacity fault evidence. The unified-data model therefore needs a **dependency-kind distinction** (start-blocking vs acceptance-blocking vs informational) alongside freshness and explicit authority. Separately, a suspected AI PID-reuse → Runner `agent_alive` false-positive is **UNVERIFIED**; the bridge is collecting minimal exact identity evidence — no product-bug verdict before that material exists.

## 4. Candidate directions for dot (options; no preselection — including no preselection of a registry)
