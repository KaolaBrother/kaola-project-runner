## Findings

1. **Provider backends are implemented in the server.** `apps/server/src/provider/ProviderDriver.ts` defines the per-instance driver SPI: drivers decode config and `create(...)` a scoped `ProviderInstance`. `ProviderInstance` includes an `orchestrationAdapter`; for example `ClaudeDriver.create` calls `createClaudeAdapterV2`. The `ProviderDriver` is the instance factory boundary; the orchestration adapter provides the session/turn behavior. [ProviderDriver.ts](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/apps/server/src/provider/ProviderDriver.ts#L75) · [ClaudeDriver.ts](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/apps/server/src/provider/Drivers/ClaudeDriver.ts#L110)

2. **The V2 adapter registry routes by provider instance.** `apps/server/src/orchestration-v2/builtInProviderAdapterDrivers.ts` lists Codex, Claude, Cursor, OpenCode, Grok, Pi and ACP Registry adapter drivers. `ProviderAdapterRegistry.layerFromProviderInstanceRegistry` dynamically resolves an instance’s `orchestrationAdapter`, so provider instance state and adapter selection share one registry. [Built-in adapter drivers](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/apps/server/src/orchestration-v2/builtInProviderAdapterDrivers.ts#L24) · [ProviderAdapterRegistry.ts](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/apps/server/src/orchestration-v2/ProviderAdapterRegistry.ts#L74)

3. **`ProviderAdapterV2Shape` is the actual execution interface.** It exports `getCapabilities`, `planSelectionTransition` and `openSession`. Its session runtime carries `events: Stream<ProviderAdapterV2Event, ...>` and optional `subscribeEvents`; turn operations include `ensureThread`, `resumeThread`, `startTurn`, `steerTurn`, `interruptTurn` and `respondToRuntimeRequest`. Concrete implementations include `Adapters/ClaudeAdapterV2.ts`, `Adapters/CodexAdapterV2.ts` and `Adapters/AcpAdapterV2.ts` (`makeAcpAdapterV2`). [ProviderAdapter.ts](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/apps/server/src/orchestration-v2/ProviderAdapter.ts#L476) · [ClaudeAdapterV2.ts](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts#L3019) · [AcpAdapterV2.ts](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/apps/server/src/orchestration-v2/Adapters/AcpAdapterV2.ts#L1463)

4. **`ProviderSessionManagerV2Shape` owns live session lifecycle.** Its exported methods open/get/close sessions, close an instance, release a session with a reason, and detach a thread. It opens through `ProviderAdapterRegistryV2`; its event pump consumes the runtime stream and fans events out to run subscribers, while persisting session updates and runless requests. [ProviderSessionManager.ts](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/apps/server/src/orchestration-v2/ProviderSessionManager.ts#L157) · [event pump](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/apps/server/src/orchestration-v2/ProviderSessionManager.ts#L1679)

5. **Run events pass through routing and normalization before persistence.** `RunExecutionServiceV2` subscribes to a session’s event stream, routes/filter events for the run, then calls `ProviderEventIngestorV2.ingestNormalized`. `ProviderEventIngestorV2Shape` exposes `normalize` and `ingestNormalized`; the normalizer maps adapter events such as `provider_thread.updated`, `provider_turn.updated`, messages/items and terminal events into orchestration domain events, with run/thread ownership guards on writes. [RunExecutionService.ts](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/apps/server/src/orchestration-v2/RunExecutionService.ts#L919) · [ProviderEventIngestor.ts](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/apps/server/src/orchestration-v2/ProviderEventIngestor.ts#L199)

6. **The event log and live stream are separate exported services.** `EventSinkV2Shape` writes committed domain events and exposes streams; its implementation combines catch-up reads with live pub/sub. `EventStoreV2Shape` appends and reads sequenced stored events. The V2 event union itself is declared in `apps/server/src/orchestration-v2/ProviderAdapter.ts`; persisted orchestration domain/stored event schemas are in `packages/contracts/src/orchestrationV2.ts`. [EventSink.ts](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/apps/server/src/orchestration-v2/EventSink.ts#L73) · [EventStore.ts](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/apps/server/src/orchestration-v2/EventStore.ts#L50) · [adapter event union](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/apps/server/src/orchestration-v2/ProviderAdapter.ts#L78)

7. **Thread streaming is a contracts/client path over the stored events.** `packages/contracts/src/orchestrationV2.ts` exports `ORCHESTRATION_V2_WS_METHODS.subscribeThread`, `OrchestrationV2SubscribeThreadInput` (including optional `afterSequence`) and `OrchestrationV2ThreadStreamItem` (snapshot, event, synchronized marker, or unknown event). `packages/client-runtime/src/state/threads.ts` subscribes using that method. Server `ThreadStream.ts` chooses replay versus snapshot and bounds replay; `orchestration-v2/http.ts` serves snapshots for clients to resume over WebSocket. [Contracts](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/packages/contracts/src/orchestrationV2.ts#L3135) · [client state](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/packages/client-runtime/src/state/threads.ts#L830) · [ThreadStream.ts](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/apps/server/src/orchestration-v2/ThreadStream.ts#L62) · [HTTP snapshot path](https://github.com/pingdotgg/t3code/blob/365aa87982a4d81cc8e0c085e8d1a40ca7daecdc/apps/server/src/orchestration-v2/http.ts#L62)

8. **`infra/relay` is the cloud connectivity/service layer around environments.** `infra/relay/src/worker.ts` builds a Cloudflare Worker and mounts client, server, mobile and other Relay API groups. `EnvironmentConnector` provides environment connect/status operations; `HookForwarder` proxies hooks to an environment and can hold requests for endpoints configured for offline holding; the server API also accepts signed agent-activity publication. This is the relay’s place in the architecture; the provider adapters, sessions and orchestration event stream are in `apps/server`.
