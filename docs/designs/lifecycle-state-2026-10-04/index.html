PROJECT RUNNER / DESIGN NOTE

让 Host 专注判断。
让状态持续可信。

Sideagent 执行派发与流程维护，脚本把更新变成可核对的操作，JSON 只保存当前责任和状态。每个角色在正确时机看到自己需要的信息。

优先目标：效率 · 正确性 · 可恢复性
减少无效的信息处理，不以总 token 下降作为成功标准。

01 / RESPONSIBILITY

决定权与维护执行权分开

用户决定授权和特殊要求。Host 保留项目判断与验收权；Sideagent 在已有范围内选配、派发、收集与回收。

Sideagent + 状态工具维护关联：任务 ↔ 派发记录 ↔ 精确会话 ↔ 授权 / on hold

同一项目仅一个活跃维护 Sideagent。用户指定其型号即授权此角色；它不占 worker 席位。并行调研助手按 worker 管理，实际资源限制仍适用。

02 / LIFECYCLE

每种对象都有开始、接续和结束

任务完成、会话停止、授权有效、服务可用是不同事实。通过关联管理，避免把它们混成一个“完成”或“失败”。

    任务状态

    工作做到哪里

    待执行、执行中、待验收、待收尾；等待原因另外记录。返修沿用原任务关联。

    授权状态

    用户允许做什么

    有效、暂停、到期或撤销。on hold 不撤销授权，停止会话也不自动撤销授权。

    运行事实

    实际上发生了什么

    实际模型、启动、发送、返回、停止来自 Runner 回执。未知保留未知，不猜成功。

    04 / STATE & TOOLS

    JSON 存状态，脚本维护，回执作证

    沿用两份项目状态文件。状态写入按记录执行，读取按角色展示；不建立第三套权威账本。

    Delegator 状态

    .kaola/delegator-heartbeat.json

    目标、用户授权来源、待采纳指令、Host 绑定、工作时段与巡查间隔、开工及日收口安排。

    跨平台接手仍读取同一路径。

    项目运行状态

    .kaola/heartbeat-prompt.json

    当前任务、派发关联、有效授权投影、Sideagent 绑定、on hold、告警与下一步。

    Host 接收生成的概览，不注入完整运维记录。

    用户特殊要求

    AGENTS.md · 用户特殊要求区

    只收录用户明确提出或确认的项目要求。新要求替换冲突旧项，历史由 Git 留存。

    Agent 可提建议，未经用户确认不加入。

    脚本负责确定性工作

    • 按记录更新，原子写入并检查并发冲突。
    • 从已有回执提取身份、实际配置和操作结果。
    • 校验引用关系，指出陈旧、缺失或不一致。
    • 生成角色视图、固定报告与定时入口。

    Agent 保留判断能力

    • Host 决定范围、所需能力、取舍与验收。
    • Sideagent 判断适配候选和证据支持的运行状态。
    • 故障影响限定范围，未知不伪装成确定失败。
    • 普通维护异常给 warning，不停无关任务。
    JSON 膨胀如何控制，旧项目如何升级？
    • 同一任务、告警或故障更新同一条记录，不逐次追加巡查历史。
    • 确认验收、适用收尾与回收后退出当前集合；终态保留在既有证据中。
    • JSON 引用日志、回执、Git / Issue / KW，不复制全过程；Host 只读角色概览。
    • 事件更新与既有巡查共同检查维护缺口；未解决责任不能为缩小文件而删除。
    • 升级时识别旧格式，在安全交接点迁移有效状态并核对真实在途工作；不重置任务、不盲重派、不默认重新规划整个项目。

    真实并行任务增多时，状态可以合理增长。目标是去掉重复与历史堆积，不是固定字节数。以上为拟实现设计，当前版本尚未部署。

    05 / SUPERVISION

    入口固定，状态动态，报告完整

    原生定时消息只保存官方文件定位句。频率和工作时间用原生定时字段设置，并记录在 Delegator 状态中。

    每次巡查的固定路径

    1. 核对实际定时正文与已安装标准模板。
    2. 读取 Skill、用户特殊要求和两份状态文件。
    3. 核对最新指令采纳、Host 进展与回收情况。
    4. 由 Sideagent / 工具维护变化与未决状态。
    5. 按固定栏目汇报，保留下一步。
    模板不符：修正并读回后继续该次巡查。无法核实就如实报告；紧急停止与在途任务不被模板问题拖住。

    每次向用户汇报

    1. 用户特殊要求：完整逐项列出。
    2. 特殊情况：on hold、告警、重大待决事项。
    3. 正在做的任务。
    4. 待做的任务。
    5. 本轮成果与下一步。

    无内容写“无”；来源缺失明确标注。未解除的 on hold 与告警每轮继续列出，不能因“已经提醒过”而消失。

    建议告警级别触发依据处理方式
    关注证据缺失、状态存在待核实的不一致Sideagent 核实；保留未决项
    警告已证实影响进展、重复失败或约定产出未正常推进明确影响、责任和下一步；相关项目判断交 Host
    严重无法安全接续、关键控制角色失效或必须由用户决策及时通知负责角色，经 Delegator 上报用户

    以证据和影响判断，不因时间长自动升级。已读、已确认或开始处理都不等于解决；同一告警持续更新，避免重复注入。

    06 / DELIVERY

    用实际接续能力验收

    在既有检查框架中验证关键路径，并做真实运行。成功标准是信息及时、责任不断、错误可纠正。

    01正常任务、无 issue 任务、完成但保留 issue open
    02fan-out 部分成功、发送未知、重复或迟到结果
    03QA 返修保持原任务；停止与回收有真实证据
    04合适席位忙则等待；缺 Expert 授权主动上报
    05授权改变、取消、on hold 与技术恢复不混淆
    06Sideagent 更换不杀在途 worker、不重复派发
    07Host 跨平台恢复与双角色故障能够接续
    08并发写入、旧数据覆盖、断链与大状态投影
    09定时模板核对、完整报告、未解除告警持续可见
    10多轮运行中无需用户提醒即可纠正陈旧状态
    实施将替换现有职责与重复文案，保留 KW 生命周期、真实回执和既有恢复能力。当前页面说明的是设计，不代表已经部署或通过这些测试。
    本轮观察与设计依据
    • VRPAI：运行可用性曾需用户提醒才纠正；OpenCode 的配置偏差已经披露，但后续仍发出任务。
    • VRPCAD：状态文件接近现有载体上限，历史记录与当前责任混在一起。
    • 源码审查：嵌套派发的事件目标、角色计数和子进程清理需要协同修改，不能只改提示词。
    • 设计讨论：外层亲审与 Claude Code Opus Extra High 已达成共识。简版文档无实质分歧；该结论不代表已获实施授权或已通过运行验证。
