# KPR 生命周期与状态维护设计

2026-10-04 · 外层与 Claude Code Opus Extra High 已达成设计共识；待用户审阅，尚未实施

## 1. 目标

让 Host 专注项目计划、判断和验收；让 Sideagent 执行派发与流程状态维护。各角色及时获得足够的信息，任务、授权与运行事实始终能够关联和恢复。衡量效率与正确性，不以总 token 数下降为目标。

## 2. 角色分工

| 角色 | 决定或执行什么 | 默认看到什么 |
|---|---|---|
| 用户 | 授权、项目特殊要求、登录与重大选择 | 进展、异常、影响与待决事项 |
| Delegator | 监管 Host、传达用户变化、恢复 Host、核对并执行自身原生定时安排 | 用户要求、项目进展、所有未解除告警与 on hold |
| Host | 目标、任务分解、能力需求、依赖、验收与适用收尾决定 | 必要全局概览和需要判断的事项 |
| Sideagent | 授权内选配、实际派发、收集、状态更新、告警与精确回收 | 与维护有关的授权、profile、运行事实及证据 |
| Worker | 被分配的研究、实现、测试或评审 | 本任务范围、必要资料与交付要求 |

同一项目只有一个活跃的维护/派发 Sideagent。并行调研助手按 worker 管理，不作为额外免席位的 Sideagent。

Sideagent 是独立角色，不占任何 worker Class 席位。用户指定其 runtime/tier 即构成该角色的选型授权；实际账号、服务和资源限制仍然适用。Sideagent 不创造授权，不新增未经用户确认的要求，不代替 Host 验收。

普通操作确认只有在明确属于既有授权和任务范围、且符合适用工具规则时，才由 Sideagent 执行。缺授权、语义不明或必须由用户当场确认的操作，保持待决并按原权限边界上报；Sideagent 不获得新的审批权。

## 3. 文件与事实来源

| 信息 | 唯一权威来源或当前位置 |
|---|---|
| 用户特殊要求 | 项目根目录 `AGENTS.md` 的用户要求区；修改历史由 Git 保存 |
| 用户决定、Host 绑定、工作时段、间隔、开工/日收口、待采纳指令 | `.kaola/delegator-heartbeat.json` |
| 当前任务、授权的已采纳投影、Sideagent 绑定、on hold、告警 | `.kaola/heartbeat-prompt.json` 的结构化当前状态 |
| 派发前记录、执行关联和返回结果 | 现有派发索引与 Runner 回执 |
| 真实会话身份、实际模型、占用、停止 | 新鲜 Runner 事实；不把旧快照当实时结果 |
| Issue、提交、Workflow 历史和结果 | Forge、Git、KW 与既有产物；JSON 只保留引用 |

两份 JSON 位于项目通用目录，跨平台接手使用相同路径。Host 所见概览是派生视图，不是第三份可独立修改的权威状态。不会复制 GitHub backlog、KW mission ledger 或创建 Sideagent 私有账本。

## 4. 维护方式：JSON + 脚本 + Sideagent

新增或扩展一个小型状态工具，提供读取视图、按记录更新、退休记录、套用已确认用户要求和核对定时入口等操作。

- **脚本处理事实与一致性**：提取已有回执；核对关联；按记录原子更新；检查版本冲突；生成角色视图和报告。旧版本不能静默覆盖新决定。
- **Sideagent 处理日常维护**：依据事件、结果和已有决定调用工具；跟踪未完成任务、故障和告警；状态变更带来源。
- **Host 保留项目判断**：验收、返修、取消等决定由 Host 给出，Sideagent 按明确的 Host 回合来源记录，并在 Host 下次视图中回显，便于发现误记；必要时 Host 可用直接工具路径记录自己的决定。
- **Delegator 保留用户与平台边界**：原生定时器通过其可用 API 核对，用户决定由其确认。日常字段维护尽可能交给 Sideagent/工具。

发生写入冲突时返回当前值和未应用的变更，由维护者据证据归并；不覆盖整个文件、丢弃未完成责任或堆入历史正文。

## 5. 最小状态关联

每个当前任务记录：稳定 ID、来源、目标与范围、能力需求、依赖、验收/收尾条件、阶段、等待原因、派发索引、证据和下一步。

每个派发项关联：所属任务、授权 preset/shared seat、实际 session/holder、输出位置、启动/发送/返回/停止回执。一个任务可包含能力要求不同的执行分支。

**授权、占用、任务阶段、服务可用性分别记录或读取。** on hold 不撤销授权；进程停止不删除未完成任务；第一个并行结果返回不代表整体完成。

## 6. 生命周期

### 任务与执行者

待执行 → 执行中 → 待验收 → 待收尾 → 完成退出。

1. Host 定义任务与验收依据。
2. Sideagent 在外部派发前建立现有索引，按授权/profile/实际可用性选配并派发。
3. 收集各分支结果，保留失败、未知和在途项。
4. Host 决定通过、局部接受、返修或取消。未完成范围不能被局部接受掩盖。
5. 完成适用收尾，核实当前职责结束的执行者已停止，或明确交接到另一持续职责。
6. 结果可从既有证据发现后，任务退出当前视图。

返修保留原任务关联，不为每次失败新建任务。无 issue、接手已有 issue、任务完成但 issue 保持 open 都是合法路径；KW 的 claim/ledger/finalize 仍由对应 owner 执行。

### Sideagent

Host 启动 → 读取共享当前状态 → 持续执行维护委托 → 必要时安全更换 → 委托结束回收。

单次回复结束不等于维护职责结束。更换时保住在途 worker，替代者从现有状态和回执接续；不反复重派，也不无限依赖旧上下文。故障由 Host 的直接工具路径处理，不能要求失败的 Sideagent 先修改自身状态。

### Host / Delegator

Delegator 核实授权与唯一 Host 后启动或附加；Host 故障时按既有恢复规则接续任务。跨平台切换保留项目记录与存活会话关联。Host 与 Sideagent 同时失效时，Delegator 先恢复 Host，再恢复 Sideagent。

日收口暂停新认领、保留在途并核实接收；连续工作按用户要求省略日收口。项目最终边界完成后，再依授权停止角色和定时器。

## 7. 派工和等待

- Host 描述工作需要的能力；Sideagent 在当前授权、profile 和真实容量内选配。
- 适合分开的研究、取证、边界探索和测试，优先考虑多个合适 Worker 并行；依据任务与可用性合理分散，不为均摊制造任务。
- 复杂判断可交合适的已授权 Elite/Expert；其支持分支不必全部使用同一 Class。
- 符合要求的席位全部忙：记录容量等待，不降级、不扩席；释放后重新评估并推进。
- 确需 Expert 而无适用授权：Host 主动提出需求，Delegator 向用户请求。已有常设授权则在范围内使用；已有授权但忙则等待。
- 用户暂停授权、缺授权、容量占满和 on hold 分开处理，不把用户暂停自动变成反复请求恢复的理由。

对派发项明确承担的 Host 能力要求，可在计划执行前核对选择是否匹配；这仅约束该派发项，不是底层 Runner 的新通信门禁，也不是对所有分支机械比较 Class。未声明要求不等于已证明适配，候选汇总仍须说明各要求由哪些执行项满足。

## 8. On hold、恢复与告警

确认额度、限流、认证、ACP 或配置故障后，维护受影响的最小范围，保留用户授权。记录原因、证据、影响、处理责任、恢复条件和下一步。

| 情况 | 后续处理 |
|---|---|
| Expert 额度/限流 | 上报用户；不自行跨 Class 替代 |
| Elite 额度/限流 | 其他已授权且适配的 Elite 接手；无候选则上报 |
| Worker 额度/限流 | 其他适配 Worker 接手；无候选则上报 |
| Host 不可用 | Delegator 按有效恢复规则处理；ZCode 也耗尽时交用户 |
| Sideagent 故障 | Host 可从可用 Worker 预设启动替代 Sideagent；该 runtime 在 Sideagent 恢复范围 on hold |
| 登录/认证失败 | 暂停受影响席位并交用户，永不尝试登录、重登或换凭证 |
| 技术适配/配置故障 | 在已授权修复范围内处理，以同范围有效证据恢复 |
| 连接等待或原因未知 | 观察与核实，不编造明确拒绝原因，不盲重派 |

接手成功不会解除原 hold。额度重置时间不自动解禁；用户允许核查后进行有界验证。恢复不扩大授权，也不复活已撤销或到期的授权。

建议告警分为关注、警告、严重三级，依据实际影响和证据判断，不因经过多久自动升级。名称与判据供用户审阅调整。普通 warning 不阻断无关工作。已读、已确认、开始处理不等于解决；未解除项在后续适用事件和每次 Delegator 巡查继续可见，重复通知合并，不另造循环注入器或调度器。

## 9. 信息流与故障接续

保留真实启动者身份，将“谁派出”与“事件送给谁”分开。现有 Host holder 承接工作事件，Sideagent 处理普通维护；需要项目判断或恢复的事项才唤醒 Host。

日常闭环为：事件到达 → Sideagent 读取相关任务与真实回执 → 工具更新受影响记录 → 生成视图 → 将需判断的事项持久记录并通知对应角色。收到通知不清除待决责任；同一问题在后续巡查继续可见，直到采纳或解决有证据。

Sideagent 更换不能连带终止健康 worker。清理必须依据精确身份保护 holder、原生 agent 及其关联进程；旧 Sideagent 的迟到清理不得解除新绑定。

Host 更换后的通知目标需要安全接续，不能只为改变通知地址而重启健康 worker。通知只是唤醒线索，执行事实仍从原回执和派发索引恢复。实现必须验证跨平台、部分失败、重复事件及通知丢失后的重建路径。

## 10. Host 的有限全局视图

默认只提供：有效目标与用户约束、任务进展与依赖、关键结果与验收缺口、能力/容量、等待原因、项目风险影响、待决事项与下一步。

视图带来源和新鲜度；使用时刷新相关事实，读不到就显示未知。日志、协议错误、账号细节、完整执行记录不常驻 Host 上下文，需要时按引用查看。项目本身是协议修复时，相关技术事实属于任务资料。

## 11. 固定心跳与报告

原生定时正文只保留已安装模板的 JSON 定位句。标准 Skill 规定完整巡查步骤；频率、时段和日收口记录在 Delegator JSON，原生定时字段按它设置。

模板不匹配时先修正并读回，再继续该次巡查；不可核实时如实报告。这个边界不延误紧急停止，不停止在途工作，不阻断无关用户任务。

每次报告固定包含：

1. 用户特殊要求，完整逐项列出。
2. 特殊情况：on hold、告警、重大待决事项。
3. 正在做的任务。
4. 待做的任务。
5. 本轮成果与下一步。

空项写“无”，缺失来源明确指出。未解除异常每次继续报告。用户新指令替换冲突旧要求，并核实实际采纳；仅收到消息不算已执行。

## 12. 最小落地与验收

修改既有状态/派发工具、事件载体和相关 Skill，替换过时职责与重复提示；不再叠加一套并行流程。已有用户要求若来源清楚，不因迁移重复请求确认。旧项目在安全边界迁移，保留一次必要原始证据和未知项。

重点验收：正常/无 issue/keep-open 任务、混合能力 fan-out、容量等待与 Expert 上报、错误实际配置、发送未知、并发状态更新、返修与回收、授权变化、各类 hold 恢复、Sideagent/Host 故障、跨平台接续、迟到事件、大状态投影、模板核对及多轮自主纠错。

本轮只交付设计。实现、真实运行验证和正式迁移尚未完成，不能据设计宣称绝对不会出错。

### 已知限制

- 脚本不能替 Host 判断一个任务是否需要 Expert，也不能凭 Class 推断所有模型能力。
- 直接手工覆盖 JSON 可以绕过规范更新；结构检查和既有回执能发现部分缺口，不能保证恢复所有被删决定。因此正常流程统一使用状态工具。
- 不同平台的原生定时器读回能力、子进程保留和升级兼容性，必须在实现后验证；不把未验证路径描述成已可靠运行。
- 新 holder 能力与状态格式在项目安全边界一并采用。大状态只包含当前责任与引用，注入内容使用投影；不能靠截断任务或用户要求适配旧载体上限。

## 13. JSON 膨胀控制与旧项目升级

### 增长受当前责任约束

1. **更新同一条记录**：按稳定任务/告警/故障 ID 更新，不把每次巡查、重试或提醒追加成新正文。
2. **完成后退出当前集合**：验收、适用收尾和执行者回收确认后，任务保留终态证据引用并退出；已解决告警同样退出。未解决责任不能因体积大而删除。
3. **证据引用，不复制历史**：日志、回执、提交和 Issue 历史留在原有来源；JSON 只保存定位信息、当前结论和下一步。用户特殊要求正文仍只有 AGENTS.md 一处。
4. **原始状态与注入内容分开**：Host 接收按角色生成的视图；详细运行状态留给 Sideagent 按需读取。状态文件变大不等于每次给 Host 的内容同样变大。
5. **维护有触发点**：派发、返回、故障、回收、用户变更触发相关更新；既有巡查核对遗漏。未正确维护的项目保留 warning，不能只靠 Agent 想起来清理。

这不能保证 JSON 永远维持固定大小：同时存在更多真实任务或未解决故障时，状态会合理增长。控制的是重复、历史和无关信息；不得靠截断必要责任满足字节预算。现有载体的整文件大小限制也须与新格式一并调整，不能只是把上限调大后继续堆记录。

### 升级现有项目

迁移义务同时纳入仓库的[版本更新规范](../../conventions.md#state-format-updates-and-migration)，不是只针对本次设计的临时说明。

新版本应在现有安装/首次加载恢复流程中识别旧 schema。先检查旧状态、用户要求来源、派发索引和 live Runner 事实，在安全交接点迁入新结构，并核对新格式与实际 holder 能力兼容。

- 有效授权、当前目标、在途/待做任务、未解决 hold 和告警必须保留并正确关联。
- 有证据证明已失效的旧指令和重复历史退出当前视图；必要的一次性迁移原始证据保留在迁移记录中。
- 来源不明或互相冲突的内容列为待核实，不能自动猜成新授权，也不能静默删除。
- 已确认的用户要求不因格式升级重复询问。会话在途时不为整理 JSON 强制重启，按已有安全恢复方式接续。
- 升级整理的是状态结构和过时信息，不重置任务、不重派已执行项、不默认重新规划整个项目。只有实际目标/约束变化或新证据表明原计划不再成立时，Host 才调整受影响计划。

以上是拟实现的迁移行为。保存本文不代表当前版本已具备自动迁移能力。
