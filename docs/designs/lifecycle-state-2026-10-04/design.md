# KPR 生命周期与状态维护设计

2026-10-04 · 外层与 Claude Code Opus Extra High 已达成设计共识；用户已授权实施，由 [#255](https://github.com/KaolaBrother/kaola-project-runner/issues/255) 承担。合并定稿（实现派工、结果定位、逐项处置、Sideagent 节点、Host 接续停止）已并入本文第 7、9、15 节。候选实现待联合验收，真实运行与正式迁移尚未全部验证

## 1. 目标

Host 负责项目计划、选配、派工原文和对原始结果的判断；工具执行 Host 采纳的派发并记录确定性事实；全新的 Sideagent 节点按有意义的批次核对流程职责、冲突与异常。各角色及时获得足够的信息，任务、授权与运行事实始终能够关联和恢复。

效率按正确完成、耗时、返工、用户介入和资源成本衡量（含重试），不以提示长度或总 token 数为目标。

## 2. 角色分工

| 角色 | 决定或执行什么 | 默认看到什么 |
|---|---|---|
| 用户 | 授权、项目特殊要求、登录与重大选择 | 进展、异常、影响与待决事项 |
| Delegator | 监管 Host、传达用户变化、恢复 Host、核对并执行自身原生定时安排 | 用户要求、项目进展、所有未解除告警与 on hold |
| Host | 目标、任务分解、能力需求、依赖、最终 preset 选择、派工原文、调用派发工具、阅读原始结果、验收与逐项处置；可直接读取、搜索、分析或完成简单的已授权工作 | 必要全局概览和需要判断的事项 |
| 工具 | 执行 Host 采纳的选择；原子记录任务/派发项/修订/会话/holder 事实；保留部分结果；生成投影；不判断产品正确性 | — |
| Sideagent 节点 | 收集并核对流程事实、套用 Host 决定、跟踪未完成职责、hold/告警、清理与回收及简短异常；不编写任务、不做分配决定、不转述结果，建议只供参考 | 与维护有关的授权、运行事实及证据 |
| Worker | 被分配的研究、实现、测试或评审，及其适用的 Workflow 认领/账本/收尾；提供原始产物并如实报告未完成范围；不改项目控制状态 | 本任务范围、必要资料与交付要求 |

同一项目同一时间只有一个活跃 Sideagent 节点。并行调研助手按 worker 管理，不作为额外免席位的 Sideagent。

Sideagent 是独立角色，不占任何 worker Class 席位。用户指定其 runtime/tier 即构成该角色的选型授权；实际账号、服务和资源限制仍然适用。Sideagent 不创造授权，不新增未经用户确认的要求，不代替 Host 验收。

托管 agent 默认以运行时支持的绕过/完全访问权限配置启动，普通文件/工具权限请求不是 Host 或 Sideagent 的日常流程。残留的权限事件属于例外恢复路径；缺授权、登录、账号或策略决定仍按原权限边界上报。Sideagent 不获得新的审批权，也不新增工具权限框架。

## 3. 文件与事实来源

| 信息 | 唯一权威来源或当前位置 |
|---|---|
| 用户特殊要求 | 项目根目录 `AGENTS.md` 的用户要求区；修改历史由 Git 保存 |
| 用户决定、Host 绑定、工作时段、间隔、开工/日收口、待采纳指令 | `.kaola/delegator-heartbeat.json` |
| 当前任务、授权的已采纳投影、Sideagent 绑定、on hold、告警 | `.kaola/heartbeat-prompt.json` 的结构化当前状态 |
| 派发前记录、执行关联和返回结果 | 现有派发索引与 Runner 回执 |
| 真实会话身份、实际模型、占用、停止 | 新鲜 Runner 事实；不把旧快照当实时结果 |
| Issue、提交、Workflow 历史和结果 | Forge、Git、KW 与既有产物；JSON 只保留引用 |

两份 JSON 位于项目通用目录，跨平台接手使用相同路径。Host 所见概览是派生视图，不是第三份可独立修改的权威状态。不会复制 GitHub backlog、KW mission ledger 或创建 Sideagent 私有账本。

## 4. 维护方式：JSON + 脚本 + Sideagent

新增或扩展一个小型状态工具，提供读取视图、按记录更新、退休记录、套用已确认用户要求和核对定时入口等操作。

- **脚本处理事实与一致性**：提取已有回执；核对关联；按记录原子更新；检查版本冲突；生成角色视图和报告。旧版本不能静默覆盖新决定。
- **Sideagent 节点核对有意义的批次**：确定性的运行事实由工具记录，不为每个普通事件启动 LLM 节点或重述已记录事实。普通 worker 返回与终止在 Host 下一个空闲边界直接交给 Host，由 Host 阅读原始结果；节点只在 Host 回合结束时承接该回合的 Host 业务变更，作为一批跟踪未完成职责、冲突和异常；状态变更带来源。
- **Host 保留项目判断**：验收、返修、取消等决定由 Host 给出并用状态工具直接记录，或由节点按明确的 Host 回合来源记录，并在 Host 下次视图中回显，便于发现误记。
- **Delegator 保留用户与平台边界**：原生定时器通过其可用 API 核对，用户决定由其确认。日常字段维护尽可能交给 Sideagent/工具。

发生写入冲突时返回当前值和未应用的变更，由维护者据证据归并；不覆盖整个文件、丢弃未完成责任或堆入历史正文。

## 5. 最小状态关联

每个当前任务记录：稳定 ID、来源、目标与范围、能力需求、依赖、验收/收尾条件、阶段、等待原因、派发索引、证据和下一步。

每个派发项关联：所属任务、授权 preset/shared seat、实际 session/holder、输出位置、启动/发送/返回/停止回执。一个任务可包含能力要求不同的执行分支。

**授权、占用、任务阶段、服务可用性分别记录或读取。** on hold 不撤销授权；进程停止不删除未完成任务；第一个并行结果返回不代表整体完成。

## 6. 生命周期

### 任务与执行者

待执行 → 执行中 → 待验收 → 待收尾 → 完成退出。

1. Host 定义任务与验收依据。
2. Host 需要委派时查询候选（当前授权、Class/profile、实际容量），选定 preset 并编写派工原文；`execute` 在外部动作前写入索引身份，再启动和发送。
3. `collect` 给出各分支的原始结果定位，保留失败、未知和在途项。
4. Host 阅读原始结果，决定通过、局部接受、返修或取消。未完成范围不能被局部接受掩盖。
5. 完成适用收尾，核实当前职责结束的执行者已停止，或明确交接到另一持续职责。
6. 结果可从既有证据发现后，任务退出当前视图。

返修保留原任务关联，不为每次失败新建任务。无 issue、接手已有 issue、任务完成但 issue 保持 open 都是合法路径；KW 的 claim/ledger/finalize 仍由对应 owner 执行。

### Sideagent

节点模式（`"mode": "node"`）：Host 绑定 → 有待处理输入时 Host 载体从记录的 Runner 参数列表启动一个全新节点 → 发送一次固定批次（worker 事件与 Host 业务修订区间）→ 节点写一次检查点核对每个输入 → 载体核对检查点并按 holder 精确停止它。下一批输入通过既有事件与空闲节拍触发下一个节点，不新增定时器，也不等待所有 worker 或 Host 的未来结论。细节见第 15 节。

节点回合结束本身不确认任何输入。节点不派发，也不重启健康 worker；节点失败由 Host 的直接工具路径处理，不要求失败的节点修改自身状态。Host 不必为每个动作往返 Sideagent。

### Host / Delegator

Delegator 核实授权与唯一 Host 后启动或附加；Host 故障时按既有恢复规则接续任务。跨平台切换保留项目记录与存活会话关联。Host 与 Sideagent 同时失效时，Delegator 先恢复 Host，再恢复 Sideagent。

日收口暂停新认领、保留在途并核实接收；连续工作按用户要求省略日收口。项目最终边界完成后，再依授权停止角色和定时器。

## 7. 派工和等待

- Host 描述工作需要的能力，按候选查询给出的当前授权、profile 和真实容量选定 preset；候选查询不创造授权，可选的规划建议在 Host 采纳前不构成派发。
- 按独立的上下文/资源边界拆分并行工作：独立来源调研、竞争假设、黑盒验证和互不竞争的重型检查可以并行；紧密耦合的实现与其相关测试放在一起，避免交接丢失上下文。不要求分类 agent、固定评审人数、每项额外 QA 阶段或无关的全分支屏障，不为均摊制造任务。
- 复杂判断可交合适的已授权 Elite/Expert；其支持分支不必全部使用同一 Class。
- 符合要求的席位全部忙：记录容量等待，不降级、不扩席；释放后重新评估并推进。
- 确需 Expert 而无适用授权：Host 主动提出需求，Delegator 向用户请求。已有常设授权则在范围内使用；已有授权但忙则等待。
- 用户暂停授权、缺授权、容量占满和 on hold 分开处理，不把用户暂停自动变成反复请求恢复的理由。
- 已记录的 on hold 覆盖某 preset 时，派发直接标为 `not-run` / `on-hold`，不再调用 Runner 重新探测。
- 实现类工作通过同一 `execute` 入口（`scope: implementation`，仅此范围允许 `mutation: true`）派给 worker；认领、worktree 和 forge 仍归 worker 的 Workflow。发送文本是 Host 原文，或 Host 的公共核心（带修订号）加逐个 worker 范围，索引记录各自哈希。

对派发项明确承担的 Host 能力要求，可在计划执行前核对选择是否匹配；这仅约束该派发项，不是底层 Runner 的新通信门禁，也不是对所有分支机械比较 Class。未声明要求不等于已证明适配，候选汇总仍须说明各要求由哪些执行项满足。

## 8. On hold、恢复与告警

确认额度、限流、认证、ACP 或配置故障后，维护受影响的最小范围，保留用户授权。记录原因、证据、影响、处理责任、恢复条件和下一步。

| 情况 | 后续处理 |
|---|---|
| Expert 额度/限流 | 上报用户；不自行跨 Class 替代 |
| Elite 额度/限流 | 其他已授权且适配的 Elite 接手；无候选则上报 |
| Worker 额度/限流 | 其他适配 Worker 接手；无候选则上报 |
| Host 不可用 | Delegator 按有效恢复规则处理；ZCode 也耗尽时交用户 |
| Sideagent 故障 | Host 可从可用 Worker 预设启动替代 Sideagent；该 runtime 在 Sideagent 恢复范围 on hold |
| 登录/认证失败 | 暂停受影响席位并交用户，永不尝试登录、重登或换凭证 |
| 技术适配/配置故障 | 在已授权修复范围内处理，以同范围有效证据恢复 |
| 连接等待或原因未知 | 观察与核实，不编造明确拒绝原因，不盲重派 |

接手成功不会解除原 hold。额度重置时间不自动解禁；用户允许核查后进行有界验证。恢复不扩大授权，也不复活已撤销或到期的授权。

建议告警分为关注、警告、严重三级，依据实际影响和证据判断，不因经过多久自动升级。名称与判据供用户审阅调整。普通 warning 不阻断无关工作。已读、已确认、开始处理不等于解决；未解除项在后续适用事件和每次 Delegator 巡查继续可见，重复通知合并，不另造循环注入器或调度器。

## 9. 信息流与故障接续

保留真实启动者身份，将“谁派出”与“事件送给谁”分开。现有 Host holder 承接工作事件，确定性事实由工具在操作边界记录，Sideagent 节点按批次核对流程职责；需要项目判断或恢复的事项才唤醒 Host。

日常闭环为：worker 事件到达 → 工具记录事实 → Host 在空闲边界读取原始结果并判断 → Host 本回合的业务写入在回合结束时成为一批，交给全新节点读取相关任务与真实回执并核对 → 生成视图 → 节点若改变了 Host 视图需关注的事项，就在 Host 下一个空闲边界唤醒 Host 一次；未改变则不唤醒。收到通知不清除待决责任；同一问题在后续巡查继续可见，直到采纳或解决有证据。

Sideagent 更换不能连带终止健康 worker。清理必须依据精确身份保护 holder、原生 agent 及其关联进程；旧 Sideagent 的迟到清理不得解除新绑定。

Host 更换后的通知目标需要安全接续，不能只为改变通知地址而重启健康 worker。Host 的 `stop`/`drain-restart` 只有显式带 `--preserve-dispatched-workers` 时才保留其派出的完整 worker 进程树，随后由继任 Host 对每个席位执行 `rebind-host`；默认停止与最终收尾语义不变。通知只是唤醒线索，执行事实仍从原回执和派发索引恢复。实现必须验证跨平台、部分失败、重复事件及通知丢失后的重建路径。

## 10. Host 的有限全局视图

默认只提供：有效目标与用户约束、任务进展与依赖、关键结果与验收缺口、能力/容量、等待原因、项目风险影响、待决事项与下一步。

视图带来源和新鲜度；使用时刷新相关事实，读不到就显示未知。日志、协议错误、账号细节、完整执行记录不常驻 Host 上下文，需要时按引用查看。项目本身是协议修复时，相关技术事实属于任务资料。

## 11. 固定心跳与报告

原生定时正文只保留已安装模板的 JSON 定位句。标准 Skill 规定完整巡查步骤；频率、时段和日收口记录在 Delegator JSON，原生定时字段按它设置。

模板不匹配时先修正并读回，再继续该次巡查；不可核实时如实报告。这个边界不延误紧急停止，不停止在途工作，不阻断无关用户任务。

每次报告固定包含：

1. 用户特殊要求，完整逐项列出。
2. 特殊情况：on hold、告警、重大待决事项。
3. 正在做的任务。
4. 待做的任务。
5. 本轮成果与下一步。

空项写“无”，缺失来源明确指出。未解除异常每次继续报告。用户新指令替换冲突旧要求，并核实实际采纳；仅收到消息不算已执行。

## 12. 最小落地与验收

修改既有状态/派发工具、事件载体和相关 Skill，替换过时职责与重复提示；不再叠加一套并行流程。已有用户要求若来源清楚，不因迁移重复请求确认。旧项目在安全边界迁移，保留一次必要原始证据和未知项。

重点验收：正常/无 issue/keep-open 任务、混合能力 fan-out、容量等待与 Expert 上报、错误实际配置、发送未知、并发状态更新、返修与回收、授权变化、各类 hold 恢复、Sideagent/Host 故障、跨平台接续、迟到事件、大状态投影、模板核对及多轮自主纠错。

验收沿用既有测试与原生证据，不新建评估框架：使用有代表性的真实任务，加少量未用于调校本改动的不同组合；区分过期/错误配置、环境噪声与真实 agent 失败，评估实际结果而非仅检查 JSON 是否合法。能力声明以已安装运行时版本、匹配的适配器和实际应用的配置/回执为据，API 文档不能证明 CLI/ACP 已支持。角色入口、渐进发现的工具参考、实际调用、身份与结果都要有证据；现有调用方核对只是本地关联，不是通用工具 ACL 或加密认证。重复或过时的指引在有证据时退休，不为每次事故新增通用规则。

实现由 [#255](https://github.com/KaolaBrother/kaola-project-runner/issues/255) 负责：状态工具为 `kaola-dispatch.py state`，规则见生成的 Project Runner 参考 `references/lifecycle-state.md` 与 `references/sideagent-node.md`。候选实现通过前，真实运行验证和正式迁移不得宣称已完成，更不能据设计宣称绝对不会出错。

### 已知限制

- 脚本不能替 Host 判断一个任务是否需要 Expert，也不能凭 Class 推断所有模型能力。
- 直接手工覆盖 JSON 可以绕过规范更新；结构检查和既有回执能发现部分缺口，不能保证恢复所有被删决定。因此正常流程统一使用状态工具。
- 不同平台的原生定时器读回能力、子进程保留和升级兼容性，必须在实现后验证；不把未验证路径描述成已可靠运行。
- 新 holder 能力与状态格式在项目安全边界一并采用。大状态只包含当前责任与引用，注入内容使用投影；不能靠截断任务或用户要求适配旧载体上限。

## 13. JSON 膨胀控制与旧项目升级

### 增长受当前责任约束

1. **更新同一条记录**：按稳定任务/告警/故障 ID 更新，不把每次巡查、重试或提醒追加成新正文。
2. **完成后退出当前集合**：验收、适用收尾和执行者回收确认后，任务保留终态证据引用并退出；已解决告警同样退出。未解决责任不能因体积大而删除。
3. **证据引用，不复制历史**：日志、回执、提交和 Issue 历史留在原有来源；JSON 只保存定位信息、当前结论和下一步。用户特殊要求正文仍只有 AGENTS.md 一处。
4. **原始状态与注入内容分开**：Host 接收按角色生成的视图；详细运行状态留给 Sideagent 按需读取。状态文件变大不等于每次给 Host 的内容同样变大。
5. **维护有触发点**：派发、返回、故障、回收、用户变更触发相关更新；既有巡查核对遗漏。未正确维护的项目保留 warning，不能只靠 Agent 想起来清理。

这不能保证 JSON 永远维持固定大小：同时存在更多真实任务或未解决故障时，状态会合理增长。控制的是重复、历史和无关信息；不得靠截断必要责任满足字节预算。现有载体的整文件大小限制也须与新格式一并调整，不能只是把上限调大后继续堆记录。

### 升级现有项目

迁移义务同时纳入仓库的[版本更新规范](../../conventions.md#state-format-updates-and-migration)，不是只针对本次设计的临时说明。

新版本应在现有安装/首次加载恢复流程中识别旧 schema。先检查旧状态、用户要求来源、派发索引和 live Runner 事实，在安全交接点迁入新结构，并核对新格式与实际 holder 能力兼容。

- 有效授权、当前目标、在途/待做任务、未解决 hold 和告警必须保留并正确关联。
- 有证据证明已失效的旧指令和重复历史退出当前视图；必要的一次性迁移原始证据保留在迁移记录中。
- 来源不明或互相冲突的内容列为待核实，不能自动猜成新授权，也不能静默删除。
- 已确认的用户要求不因格式升级重复询问。会话在途时不为整理 JSON 强制重启，按已有安全恢复方式接续。
- 升级整理的是状态结构和过时信息，不重置任务、不重派已执行项、不默认重新规划整个项目。只有实际目标/约束变化或新证据表明原计划不再成立时，Host 才调整受影响计划。

以上迁移行为由 [#255](https://github.com/KaolaBrother/kaola-project-runner/issues/255) 的 `state migrate`（默认只读计划，`--write` 才写入）实现候选；真实项目上的迁移尚未运行验证。

## 15. 合并定稿补充

本节给出 #255 合并定稿与研究细化的实现细节；前文各节已按定稿直接改写，不靠本节覆盖。研究依据保存在同目录 [research/](research/README.md)，外部参考见第 16 节。

### 派工与结果

- **一个入口**：研究、QA、报告与实现都走 `execute`。实现项是普通 worker 派工，不在工具内认领、建 worktree 或操作 forge。
- **原文发送**：每项要么发送 Host 的完整 `prompt`，要么发送计划 `core`（带 `core_revision`）加该项 `worker_scope`；索引的 `prompt_source` 记录种类、核心修订和各段 `sha256`。
- **任务关联**：带 `--state` 时，派发项 id 由工具写入任务 `dispatch`（写入者 `tool:execute`，不增加 Host 修订号）。
- **结果可定位**：`collect` 结果给出精确回合（holder、提示指纹）、Runner `capture --since <游标> --full --inline` 参数、事件日志、声明输出的种类（`file` 检查是否存在；`capture` 即回复本身；`remote` 与 `description` 不检查），以及显式缺口（`reply-text-absent`、`capture-truncated`、仅限文件的 `output-absent`）。480 字摘录标明是否截断与原长。新的返回把验收重置为 `pending` 并保留之前的值。
- **索引并发**：`execute`、`collect` 与处置镜像在同一文件锁下按派发项与字段合并写入索引，并发写入者的字段不会被整份覆盖。

### 逐项处置

任务的 `dispositions` 按派发项记录 Host 决定（`accepted`、`repair`、`cancelled`、`superseded`、`handed-off`），任务级 `verdict` 仍是整体判断。`update --index` 把处置镜像到索引 `acceptance`；有任务结论但某项没有处置时，该项标为 `undecided`，不会继续显示为 `pending`。

### Host 修订号与节点检查点

- 只有 Host 业务写入增加文件 `host_revision`；工具和 Sideagent 写入只记录 `writer_holder`。
- 节点用 `state checkpoint` 逐项核对本批输入：`applied` 必须是本节点 holder 写下的当前记录或退休记录；`retained` 必须是仍有 `next`/`owner`/`wait` 的当前记录或 Host 段落。旧证据或他人证据不能结清新输入。
- 全部结清才更新 `maintenance.last_verified`；`acked_host_revision` 不越过任何未结清的修订；之后的 Host 写入保持待处理。
- 未结清的输入一次性写入 `maintenance-returned` 告警交给 Host，不再发给其他节点，也不计为已应用。
- 载体在节点回合结束后核对检查点：已核实且 Host 视图需关注的事项相对 Host 上次所见和本批开始时都有变化，才在 Host 下一个空闲边界唤醒一次，否则保持安静；部分、缺失、修订范围低于本批（含省略 `--through-host-revision`）、节点未接收本批、启动失败或节点丢失，都把未处理的修订范围交给 Host 一次，且不再为同一范围启动节点；随后精确停止节点。启动失败或本批未被接收后，绑定改变前不再启动新节点；停止未确认时，该 holder 进程仍在则不启动新节点。旧节点的迟到写入返回 `binding-superseded`。
- 节点提示带角色限制：只写来源指针（记录 id、回执或日志路径、事件 id），不重述、概括或评判 worker 结果；不派发、启停会话、编写或分配任务，也不替 Host 授权、验收或决定。
- 最近一次已核实检查点与当前责任并列显示在 Host 与 Delegator 视图，供 Delegator 发现维护停滞；不在心跳中累积检查点历史。

### 唤醒与停止

- 发往 Host 的 worker `idle` 唤醒在未送达时与权限唤醒一样保留，Host 可达后重发；新唤醒替换旧唤醒，停止时丢弃。不新增定时器。
- 旧 holder 不支持保留意图时返回 `preserve-unsupported` 且什么都不停止，需先在空闲时 `drain-restart`。启动中途被打断的席位不在保留承诺之内，必须核对。

### 原生证据与仍未验证

隔离夹具中的原生证据：ZCode 与 Codex 上的全新节点；缺失检查点交回 Host 且不再启动节点；停止未确认与迟到确认；Codex 与 ZCode Host 的保留停止、`rebind-host` 与 worker 进程存活；无 Host 时保留的 idle 唤醒；启动中途中断（遗留 `starting` 记录，需人工核对）；Host 停止回收其节点；带节点绑定的模型驱动 Host 判断两个 worker 的原始结果，节点批次带来的新关注事项唤醒 Host。OpenCode 权限策略随 #256 合入。

仍未原生验证：部分检查点与修订范围不足（单元测试覆盖）、其他平台上的节点模式、候选模板的原生定时器读回、真实项目的迁移与状态规模。不宣称普遍无故障。
