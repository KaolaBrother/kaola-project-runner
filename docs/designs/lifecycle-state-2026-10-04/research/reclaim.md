# Kubernetes ownership and reclaim: research input for KPR #255

Accessed 2026-10-04. This is design research only; no KPR behavior was tested and no native process was started. Kubernetes API objects, node processes, and KPR ACP sessions are different evidence domains.

## Findings

**1. Ownership is tied to an object incarnation; adoption is an explicit guarded write. — Borrow now, narrowly and conditionally.**

Kubernetes UIDs distinguish historical objects even when name and kind are reused; `OwnerReference.uid` identifies the owner incarnation. In the v1.37.0 source, `ControllerRefManager` ignores a child controlled by a different UID. It adopts only an orphan that matches the selector while neither parent nor child is deleting. Deployment and Job controllers re-read the parent from the API server before adoption and reject a same-name parent whose UID differs; the adoption patch includes the child UID and new owner UID. This addresses stale-cache, delete/recreate, and competing-adopter races. [UIDs and names](https://kubernetes.io/docs/concepts/overview/working-with-objects/names/#uids), [owner reference fields](https://kubernetes.io/docs/reference/kubernetes-api/definitions/owner-reference-v1-meta/), [claim/adopt/release source](https://github.com/kubernetes/kubernetes/blob/f54c212e3a2f75d674b717a9b29052b20b60aefc/pkg/controller/controller_ref_manager.go#L1490-L1596), [Job parent recheck](https://github.com/kubernetes/kubernetes/blob/f54c212e3a2f75d674b717a9b29052b20b60aefc/pkg/controller/job/job_controller.go#L3678-L3705).

Inference for KPR: exact session identity already has stronger runtime-specific parts than a display name (canonical root, standard session name, `acp_session_id`, and native resume ID); existing assignment/return receipts supply task and revision. Kubernetes therefore supports the closure design’s exact-identity requirement, but its selector-based adoption is too broad for task authority: a matching label does not carry Host intent, authorization, or semantic acceptance.

Smallest borrowable concept: for safe Host replacement, reuse any existing explicit preservation intent. If none is sufficient, Host chooses one scoped continuation/adoption and the tool records it in the existing source of current facts: predecessor and successor Host bindings, each preserved worker’s exact locator/session identity and assignment revision, and the successor’s assumption of the remaining duty. Persist intent before retiring the predecessor. Sideagent may update locators and duties; Host still reads original results and judges them. This attaches responsibility; it does not start/stop workers, transfer a grant, or accept results. It implements the existing closure question, not a general owner graph or second registry.

QA: give the successor a worker locator with the same displayed session name but a different native/ACP ID; adoption must not bind to it or start a duplicate. Then adopt the exact live session and inject a late result from the predecessor: it remains linked to its original assignment/revision, and only the Host that reads the original result records semantic judgment. Confirm an unrelated worker is not preserved by broad labels or project membership.

**2. Orphaning, finalizers, and process survival are separate facts. — Existing receipts cover the useful boundary; defer Kubernetes finalizer machinery.**

Kubernetes background deletion removes the owner API object first and garbage-collects dependents later; foreground deletion holds the owner with a finalizer while it deletes blocking dependents; orphan propagation leaves dependents and removes the owner relationship. The docs show orphaned Deployment Pods still running. Finalizers set `deletionTimestamp` and keep an API object terminating until the responsible controller removes its finalizer. In the Job controller, `batch.kubernetes.io/job-tracking` is removed after the Pod has been accounted in Job status; an orphan cleanup path separately checks whether the Pod has been adopted or its Job finished before removing that finalizer. These are API-object lifecycle barriers and accounting evidence, not a general guarantee that an OS process has exited. [garbage collection and propagation](https://kubernetes.io/docs/concepts/architecture/garbage-collection/), [owners and dependents](https://kubernetes.io/docs/concepts/overview/working-with-objects/owners-dependents/), [finalizer contract](https://kubernetes.io/docs/concepts/overview/working-with-objects/finalizers/), [Job tracking](https://kubernetes.io/docs/concepts/workloads/controllers/job/#job-tracking-with-finalizers), [Job orphan-finalizer cleanup source](https://github.com/kubernetes/kubernetes/blob/f54c212e3a2f75d674b717a9b29052b20b60aefc/pkg/controller/job/job_controller.go#L3506-L3646).

The distinction matters operationally: graceful Pod termination is asynchronous, and force deletion explicitly does not wait for kubelet confirmation; on an unreachable node, a process can continue after its API object is gone. [Pod termination](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination), [force-delete behavior](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_delete/). The Job docs also note a special default orphan policy for unmanaged Jobs, which can leave Pods behind; this is not a universal owner-deletion rule. [Job cleanup note](https://kubernetes.io/docs/concepts/workloads/controllers/job/#clean-up-finished-jobs-automatically).

KPR fit: the closure design already separates task/result, runtime occupancy, and cleanup. Host judges original results; Sideagent keeps exact locators and duties. A returned result or requested stop cannot establish reclaim. The existing requirement for an exact stop-holder receipt plus stopped/no-residual proof is the right analogue; the Host’s sourced verdict stays separate. Do not add Kubernetes-style finalizers or treat a missing/deleted locator as proof of stop.

QA: return a worker result, then make the exact stop outcome unknown while status still shows the session live. The task may be judged from its original result, but occupancy and cleanup remain open. On Host replacement, preserve/recover the exact live session without replaying start; close reclaim only when the existing stop path reports the exact holder stopped and no residual process. Repeat with the process unreachable: keep uncertainty actionable rather than inferring either survival or death from API/session metadata alone.

**3. Reconciliation recovers missed events; retries need damping and durable open duties. — Already covered as design policy; defer Kubernetes retry limits.**

The Deployment controller’s informer comments describe periodic resync as a way to rediscover changes after a dropped event. `client-go`’s default workqueue limiter combines per-item exponential delay (5 ms base, capped at 1,000 s in this source) with a global token bucket (10 QPS, burst 100). This limits retry pressure; the Deployment controller additionally drops a key after 15 retries, so that specific cutoff is not a safe KPR pattern for unresolved work. [Deployment resync and error path](https://github.com/kubernetes/kubernetes/blob/f54c212e3a2f75d674b717a9b29052b20b60aefc/pkg/controller/deployment/deployment_controller.go#L1995-L2013), [Deployment retry cutoff](https://github.com/kubernetes/kubernetes/blob/f54c212e3a2f75d674b717a9b29052b20b60aefc/pkg/controller/deployment/deployment_controller.go#L1594-L1605), [workqueue limiter](https://github.com/kubernetes/kubernetes/blob/f54c212e3a2f75d674b717a9b29052b20b60aefc/staging/src/k8s.io/client-go/util/workqueue/default_rate_limiters.go#L857-L870).

Primary research supports the recovery/QA lesson, not a claim that reconciliation alone is correct. Sieve perturbs controller views of cluster state and reported 46 serious safety/liveness bugs across ten popular controllers. Anvil formalizes eventual progress and stability for an unchanged desired state, but makes fairness and eventual fault quiescence assumptions; its authors also report deep bugs missed by testing. [Sieve, OSDI ’22 paper](https://www.usenix.org/system/files/osdi22-sun.pdf), [Anvil, OSDI ’24 paper](https://www.usenix.org/system/files/osdi24-sun-xudong.pdf).

KPR fit: the closure design already uses operation-boundary receipts, revision-coalesced attention, existing hourly inquiry, explicit unresolved duties, and cause-specific authorized recovery; it forbids new timers and arbitrary retry counts. Kubernetes watchers and queues have different persistence and timing properties. Borrow only the principle: reconcile from current authoritative receipts/state after a missed wake, coalesce duplicates by actual revision, and prevent repeated immediate action on the same unchanged cause while retaining the open duty. Do not copy a finite retry/drop count or add a queue/scheduler.

QA: suppress a return or stop notification, then restart the Host/Sideagent; the next existing safe boundary/inquiry must discover the current receipt and duty. Deliver the same and an older event repeatedly; there is one current attention item and no duplicate start/stop. Hold a persistent cleanup failure across inquiries; it remains one actionable duty with its source error, causes no cold-start storm, and clears only on exact evidence or explicit authorized disposition.

## Boundaries and disposition

The only conditional addition suggested is a scoped Host-replacement continuation receipt if the existing preservation intent cannot express successor responsibility. Reuse the design’s existing exact locators, assignment identities, index/receipts, and Workflow sources. Orphan-by-selector adoption, Kubernetes finalizer objects, Job lifecycle policy, retry cutoff, and extra reconciliation timers are deferred because they encode Kubernetes API-controller semantics and would add mechanisms KPR does not own. These findings inform later design/QA; they do not validate the KPR candidate or authorize implementation.
